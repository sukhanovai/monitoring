# Расширение `mail_cert_monitor` — сертификат почтового сервера (Zimbra)

Расширение следит за развёртыванием TLS-сертификата почтового сервера Zimbra
по письмам скрипта развёртывания. Сертификат выпускает certbot на `sr-web-fe`,
скрипт переносит его в контейнер с Zimbra, проверяет и шлёт письмо.

**Скрипт молчит, пока всё в порядке.** Письмо приходит только при замене
сертификата или при проблеме, поэтому каждое письмо — это событие, по которому
сразу уходит оповещение. Отдельный heartbeat не нужен: если цепочка где-то
сломалась, за 14 дней до конца срока придёт `EXPIRING`.

## Формат темы письма

```
CERT <OK|WARN|CRIT> <хост> CT<id> <СОБЫТИЕ> [key=value …]
```

Регулярное выражение (`BACKUP_PATTERNS["mail_cert"]`, именованные группы):

```
^CERT (?P<level>OK|WARN|CRIT) (?P<host>\S+) CT(?P<ct>\d+) (?P<event>[A-Z_]+)(?P<params>.*)$
```

Паттерн из исходного предложения без имён групп
(`^CERT (OK|WARN|CRIT) (\S+) CT(\d+) ([A-Z_]+)(.*)$`) тоже работает: группы
берутся по позициям. Хвост темы разбирается как пары `key=value`; `until=`
(дата `YYYY-MM-DD`) и `days=` сохраняются отдельно.

| Тема | Значение |
|------|----------|
| `CERT OK sr-pve2 CT101 DEPLOYED until=2027-01-22 days=89` | новый сертификат установлен и проверен |
| `CERT WARN sr-pve2 CT101 EXPIRING days=13` | до конца срока меньше 14 дней, а certbot на sr-web-fe не продлил |
| `CERT CRIT sr-pve2 CT101 DEPLOY_FAILED rc=1` | развёртывание не прошло, Zimbra отдаёт старый сертификат (лог в теле письма) |
| `CERT CRIT sr-pve2 CT101 SRC_MISSING file=cert.pem` | на sr-web-fe нет файлов сертификата |
| `CERT CRIT sr-pve2 CT101 SRC_EXPIRED` | на sr-web-fe лежит просроченный сертификат |
| `CERT CRIT sr-pve2 CT101 SAN_MISMATCH` | в сертификате нет mail.202020.ru |
| `CERT CRIT sr-pve2 CT101 KEY_MISMATCH` | ключ не соответствует сертификату |
| `CERT CRIT sr-pve2 CT101 NOT_RSA` | certbot выдал ECDSA, нужен `--key-type rsa` |
| `CERT CRIT sr-pve2 CT101 CT_DOWN` | CT 110 или CT 101 не запущен |

Тело письма (лог развёртывания) хранится (до 4000 символов). Последние
1500 символов лога попадают в оповещение по `WARN`/`CRIT`.

## Как это работает

1. `mail-monitor` разбирает письмо (`modules/mail_parts/parsers/mail_cert.py`,
   до всех остальных парсеров: паттерн заанкорен) и пишет событие в таблицу
   `mail_cert_events` в `backups.db`. Одно и то же письмо повторно не
   сохраняется (`UNIQUE(email_subject, received_at)`).
2. Основной цикл мониторинга (`core/monitor_parts/lifecycle.py` →
   `check_mail_cert_alerts`) рассылает оповещение по каждому новому событию
   ровно один раз (`notified = 1`). Уровень: `CRIT` → критическое, `WARN` →
   предупреждение, `OK` → информационное. Категория оповещения —
   `mail_cert_monitor` (подписка настраивается в «Мои оповещения»).
3. В тихие часы оповещения не теряются: события ждут окончания тихого режима.
   События старше 48 часов на момент рассылки (например, накопленные, пока
   основной цикл не работал) отмечаются без отправки.
4. **Подстраховка на случай, если сломался сам скрипт.** Срок из последнего
   письма с `until=` известен. Если последнее событие — `OK`, а до конца срока
   осталось ≤ 7 дней (значит, `EXPIRING` так и не пришёл), мониторинг сам
   присылает предупреждение «срок подходит к концу, а писем нет» — раз в сутки.

## Где смотреть

- **Telegram:** главное меню → «📨 Сертификат почты»: состояние по каждому
  серверу/CT, срок действия, последние события, история и справка по событиям.
- **Matrix:** команда `!mailcert` (или кнопка-реакция 📨 в `!extensions`).
- **Веб-интерфейс:** «Операции» → «📨 Сертификат почты» (действие
  `mail_cert_monitor_status`; то же действие доступно мобильному клиенту через
  `POST /v1/control/actions`).
- **Утренний/ручной отчёт:** секция «📨 Сертификат почтового сервера»
  (включается в «Состав отчёта»).

## Настройка

- Включение/выключение — в списке расширений (Telegram, Matrix `!extensions`,
  веб, Android). Выключенное расширение не разбирает письма и не шлёт оповещения.
- Паттерн темы — раздел `mail_cert` в `BACKUP_PATTERNS` (Matrix `!settings`)
  или строки `category='mail_cert'` в таблице `backup_patterns`. Эталонный
  паттерн проверяется всегда, поэтому сломанный пользовательский паттерн
  разбор не ломает.

## Требования к скрипту

- Тема — ASCII, одна строка, без префиксов `Re:`/`Fwd:`.
- Письмо доставляется в Maildir сервера мониторинга так же, как остальные
  отчёты (например, через `katok@202020.ru` и фильтр пересылки).
- `until=` — дата окончания нового сертификата (`notAfter`) в формате
  `YYYY-MM-DD`; без неё подстраховка по сроку не работает.
