# Расширение `ids_cert_monitor` — IDS и сертификат почты

Расширение принимает письма двух скриптов на хосте Proxmox `sr-pve2`:

- **IDS** (`/root/ids101/ids101.sh`) — мониторинг взлома контейнеров. Сейчас
  это CT101, почтовый сервер Zimbra; позже добавятся другие CT. Проверки
  делает хост, а не сам контейнер, поэтому скомпрометированный CT не может
  их отключить.
- **CERT** (`/root/certsync/mail-cert-sync.sh`) — автоматическая замена
  TLS-сертификата почтового сервера.

**Главное требование:** письмо о проблеме безопасности не должно потеряться.
Любая ошибка разбора — отдельное оповещение, а не строка в логе. Тишина
мониторинга (сломан хост, cron, почта) не выглядит как «всё хорошо»: её ловят
сторожевые проверки.

## Формат письма

Тема:

```
^(IDS|CERT) (OK|WARN|CRIT) (\S+) CT(\d+) ([A-Z_]+)(?: (.*))?$
```

`IDS CRIT sr-pve2 CT101 INTRUSION n=3 types=EXEC_FROM_TMP,FAKE_KTHREAD` →
source `IDS`, level `CRIT`, node `sr-pve2`, ct `101`, event `INTRUSION`,
поля `n=3`, `types=…`.

Тело: строки `ключ=значение` до пустой строки — метаданные (`level`, `node`,
`ct`, `event`, `time`), после неё — детали в свободной форме. В оповещение
попадают первые 25 строк деталей, не больше 3000 символов.

Время события берётся из заголовка `Date`, если его нет — из `time=` в теле,
если нет и его — время получения.

Письмо, которое начинается с `IDS ` или `CERT `, но не подходит под
регулярное выражение, даёт WARN «нераспознанное письмо IDS/CERT».

## События

### IDS

| event | Семейство | Действие |
|---|---|---|
| `INTRUSION` (WARN/CRIT) | `intrusion` | открыть/обновить проблему; `types=` расшифровываются |
| `RESOLVED` | `intrusion` | закрыть |
| `ZIMBRA_CONFIG` (WARN/CRIT) | `config` | открыть/обновить; `kinds=` расшифровываются, строки `+ ADMIN/FWD/REDIR/CFG` идут первыми |
| `ZIMBRA_CONFIG_RESOLVED` | `config` | закрыть |
| `DOWN`, `STALE` | `availability` | открыть (CRIT) |
| `UP` | `availability` | закрыть |
| `MONITOR_ERROR` | `monitor` | открыть (WARN) |
| `HEARTBEAT` | — | сигнал жизни; OK закрывает `availability` и `monitor`; WARN при закрытых `intrusion`/`config` открывает `intrusion` в WARN |
| `BASELINE`, `TEST` | — | только журнал |

Коды `types`: `WEB_RCE`, `FAKE_KTHREAD`, `EXEC_FROM_TMP`, `DELETED_EXE`,
`EXEC_IN_TMP`, `UID0`, `FW_OUT_DROP`, `WEB_EXPLOIT` (CRIT); `FILE_CHANGED`,
`NEW_PORT` (WARN).

### CERT

| event | Действие |
|---|---|
| `DEPLOYED` | закрыть проблему `cert`, запомнить `until=` (дату окончания) |
| `EXPIRING`, `DEPLOY_FAILED`, `SRC_MISSING`, `SRC_EXPIRED`, `SAN_MISMATCH`, `KEY_MISMATCH`, `NOT_RSA`, `CT_DOWN` | открыть проблему `cert` |

CERT-скрипт молчит, пока всё в порядке, и heartbeat не шлёт.

## Автомат состояний

Ключ проблемы: `<source>/<node>/CT<ct>/<family>`, например
`IDS/sr-pve2/CT101/intrusion`. Состояние `OK`/`WARN`/`CRIT` хранится в
`backups.db` (таблица `ids_state`) и переживает перезапуск.

- OK → WARN/CRIT — оповещение.
- Тот же уровень, детали те же — ничего (дубликат); детали изменились —
  оповещение «обновление».
- Повышение WARN → CRIT — оповещение «повышение».
- CRIT не понижается до WARN без закрывающего события: детали обновляются,
  уровень остаётся.
- Закрывающее событие при открытой проблеме — 🟢 с длительностью проблемы.
- Письмо старше (по `Date`) последнего письма по тому же ключу состояние не
  меняет, только попадает в журнал (защита от перепутанного порядка доставки).
- Повтор того же `Message-ID` игнорируется.

## Оповещения

| Ситуация | Как |
|---|---|
| CRIT | сразу, мимо тихих часов (`force`), уровень «критическое» |
| WARN `intrusion`/`config` — новая проблема, обновление | сразу, мимо тихих часов (`force`), уровень «предупреждение»: признак взлома не должен ждать утра |
| остальные WARN (в т.ч. напоминания) | обычное оповещение; в тихие часы ждёт их окончания |
| Восстановление | обычное (информационное) оповещение |
| `BASELINE`, `TEST`, первый `DEPLOYED` | только журнал |
| Нераспознанное письмо / ошибка обработки | WARN |

Напоминания, пока проблема не подтверждена: CRIT — каждые 2 часа, WARN — раз
в 12 часов, с длительностью и последними деталями. **«✋ Подтвердить»**
(Telegram, Android, веб, Matrix `!ids ack`) останавливает напоминания по
проблеме, но не закрывает её: закрывает только событие от IDS (`RESOLVED`,
`ZIMBRA_CONFIG_RESOLVED`, `UP`, OK-`HEARTBEAT`). Новая проблема или повышение
уровня снимают подтверждение.

Для `IDS` + `CRIT` + `INTRUSION` в оповещение добавляется строка
«Что делать: изолировать CT — `ip link set veth<ct>i0 down` (на <node>)».

Категория оповещений — `ids_cert_monitor` («🛡️ IDS и сертификат почты» в
«Мои оповещения»).

Письма разбирает mail-monitor, а рассылает основной цикл мониторинга. Связь
между ними — очередь `ids_outbox` в `backups.db`. Неотправленное за 48 часов
помечается как просроченное. Цикл рассылает IDS/CERT и тогда, когда
мониторинг серверов поставлен на паузу.

## Сторожевые проверки (раз в 5 минут)

1. **Нет HEARTBEAT больше 2 часов** → `IDS/<node>/CT<ct>/watchdog` в CRIT
   («нет сигнала жизни от IDS N часов: сломан хост, cron, отправка почты или
   хост скомпрометирован»). Закрывается следующим HEARTBEAT.
2. **Ожидаемый источник молчит.** Если от источника из `IDS_EXPECTED_SOURCES`
   HEARTBEAT не пришёл ни разу за 2 часа после запуска мониторинга — тот же CRIT.
3. **Срок сертификата.** Если до `until` из последнего `DEPLOYED` осталось
   меньше 10 дней → `CERT/<node>/CT<ct>/cert_watchdog` в CRIT («сертификат
   истекает <дата>, автозамена не сработала»). Закрывается `DEPLOYED` с более
   поздней датой.

## Журнал

Каждое IDS/CERT-письмо записывается в `ids_events`: время, ключ, уровень,
событие, поля, детали, итог обработки. Журнал не чистится (ТЗ требует
хранить его не меньше 180 дней). В лог mail-monitor идёт одна строка на
письмо: `IDS CRIT sr-pve2/CT101/intrusion IDS/sr-pve2/CT101/intrusion OK→CRIT notified`.

## Где смотреть

- **Android:** плашка «🛡️ IDS» (`ok/всего` контейнеров, красная при открытых
  проблемах). Тап открывает статус с кнопками «✋ Подтвердить: …», «🕘 Журнал
  30 дней», «📖 Справка».
- **Telegram:** главное меню → «🛡️ IDS и сертификат почты».
- **Matrix:** `!ids`, `!ids history`, `!ids ack [номер]`, `!ids help`.
- **Веб:** «Операции» → «🛡️ IDS и сертификат почты».
- **Утренний отчёт:** секция «🛡️ IDS и сертификат почты».

## Настройки

- `IDS_CT_NAMES` — названия CT в оповещениях, по умолчанию
  `{"101": "почтовый сервер Zimbra"}`. CT без названия выводится как `CT<id>`.
- `IDS_EXPECTED_SOURCES` — источники, от которых обязан приходить HEARTBEAT,
  по умолчанию `["sr-pve2/CT101"]`.

Обе правятся через Matrix `!settings` (группа «🛡️ IDS и сертификат почты»).
