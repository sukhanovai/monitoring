# 👥 Многопользовательский режим

Server Monitoring System v8.64.1
Версия: 8.64.1

Система собирает данные **один раз для всех**, а доставляет их **каждому
по-своему**. Этот документ описывает реестр пользователей (`core/users.py`),
персональные настройки и то, как они работают в Telegram-боте,
Matrix-command-боте, Android-клиенте и веб-API.

## Что общее, а что личное

| Общее (одно на систему) | Личное (у каждого своё) |
| --- | --- |
| Список серверов, интервалы проверок, таймауты | Состав отчёта (какие расширения включать) |
| Паттерны писем, конфиг бэкапов, БД, ZFS, остатки | Получать ли утренний/сводный отчёт |
| Учётные данные SSH/WinRM, время сбора данных | Получать ли оповещения и какие уровни |
| Включённость расширений (`extension_manager`) | Подписка на категории оповещений |
| Пороги ресурсов, общий тихий режим | Личные тихие часы |

Настройки сбора данных **нельзя** сделать персональными: попытка сохранить
их как персональные завершается `UserRegistryError`. Это гарантирует, что
пользователи не расходятся в том, ЧТО система мониторит, — расходятся
только в том, ЧТО и КУДА им доставляется.

## Модель данных

Три таблицы в `data/settings.db` (рядом с общими настройками):

```
users(id, username, display_name, role, enabled, created_at, updated_at)
user_channels(id, user_id, channel_type, channel_ref, title, enabled)
user_preferences(user_id, key, value, updated_at)
```

* `role` — `admin` (управляет реестром) или `user`.
* `channel_type` — `telegram` (chat_id), `matrix` (room_id или MXID),
  `mobile` (subject токена либо device_id), `web` (логин веб-интерфейса).
  Пара «тип + идентификатор» уникальна: один канал принадлежит ровно
  одному пользователю, повторная привязка переносит канал.
* `user_preferences` хранит только персонализируемые ключи:
  `REPORT_EXTENSIONS`, `REPORTS_ENABLED`, `ALERTS_ENABLED`,
  `ALERT_LEVELS`, `ALERT_CATEGORIES`, `QUIET_HOURS_ENABLED`,
  `QUIET_START`, `QUIET_END`.

Порядок разрешения персональной настройки:

1. значение пользователя из `user_preferences`;
2. общесистемное значение того же ключа из таблицы `settings`
   (работает как «настройка по умолчанию для всех» — например,
   `REPORT_EXTENSIONS`);
3. встроенный дефолт.

## Обновление с однопользовательской конфигурации

При первом обращении к реестру, если таблица `users` пуста, создаётся
пользователь `admin` (роль `admin`), к которому привязываются:

* все чаты из `CHAT_IDS` → каналы `telegram`;
* `MATRIX_ROOM_ID` → канал `matrix`;
* `WEB_LOGIN` → каналы `web` и `mobile`;
* текущий `REPORT_EXTENSIONS` становится личным составом отчёта админа.

До появления второго пользователя поведение системы не меняется. Если
реестр по какой-то причине недоступен или пуст, доставка автоматически
падает обратно на прежний режим (общий `CHAT_IDS` + общая Matrix-комната),
а доступ к боту дополнительно разрешается по `CHAT_IDS` — обновление
никого не отрезает от бота.

## Категории оповещений

Категория передаётся в `lib.alerts.send_alert(category=...)`:

* `availability` — доступность серверов (up/down);
* `resources` — CPU/RAM/диски;
* `system` — старт/остановка мониторинга, сервисные сообщения;
* id расширения (`backup_monitor`, `tls_cert_monitor`,
  `zfs_pool_free_space_monitor`, …) — оповещения этого расширения.

Неизвестная категория считается системной и приходит всем, у кого включены
оповещения — новое расширение не «пропадает» из-за того, что его нет в
чьей-то подписке.

Личные тихие часы не блокируют критические (`critical`) и принудительные
(`force=True`) сообщения.

## Telegram-бот

`⚙️ Настройки` →

* `🗒️ Состав отчёта` — личный состав того пользователя, которому
  принадлежит чат;
* `🔔 Мои оповещения` — отчёт/оповещения/уровни/категории/тихие часы;
* `👥 Пользователи` (админ) — список, карточка пользователя, включение и
  выключение, роль, удаление, `➕ Привязать этот чат`.

`➕ Привязать этот чат` в списке создаёт нового пользователя `tg_<chat_id>`
и привязывает к нему текущий чат — так новый получатель добавляется за два
нажатия прямо из своего чата. Если чат уже кому-то принадлежит, ничего не
переназначается: открывается карточка владельца. Перенос чата другому
пользователю делается осознанно — кнопкой `🔗 Привязать этот чат` в его
карточке.

## Права на управление реестром

Меню `👥 Пользователи` открыто чату, если выполнено любое из условий:

1. чат принадлежит пользователю с ролью `admin`;
2. чат перечислен в общем `CHAT_IDS` — до многопользовательского режима
   такие чаты имели полный доступ к настройкам бота, и молча урезать их
   права было бы неверно;
3. чат вообще не привязан к пользователю (однопользовательский режим);
4. в реестре не осталось ни одного администратора с каналом связи —
   аварийный выход, чтобы реестр нельзя было запереть.

Реестр защищён от потери управления: последнего администратора нельзя
разжаловать, выключить или удалить — сначала нужно назначить
администратором кого-то ещё. Администратор без единого канала обмена
считается недостижимым (пункт 4 выше).

Если доступ всё же потерян (например, на старой версии кнопка увела чат у
администратора), права возвращаются сами после обновления. Крайний случай —
правка БД на сервере:

```sh
sqlite3 data/settings.db "UPDATE users SET role='admin' WHERE username='tg_<chat_id>';"
```

## Matrix-command-бот

* `!report` — отчёт по личному составу владельца комнаты;
* `!report config [<ext_id>|all|none]` — личный состав отчёта;
* `!me` — личные настройки доставки и список своих каналов;
* `!users` — реестр (админ):

```
!users                                  # список пользователей и каналов
!users add <username> [Отображаемое имя]
!users link <username> <telegram|matrix|mobile|web> <идентификатор>
!users unlink <тип> <идентификатор>
!users enable|disable <username>
!users delete <username>
```

Пользователь определяется сначала по MXID отправителя, затем по комнате —
можно дать человеку личную комнату с ботом либо опознавать его в общей.

## HTTP API (Android-клиент и веб)

| Метод и путь | Назначение |
| --- | --- |
| `GET /v1/me` | Текущий пользователь, его настройки и справочник категорий |
| `PATCH /v1/me/notifications` | Изменение личных настроек доставки |
| `GET /v1/settings/report` | Личный состав отчёта (поле `scope`: `user`/`global`) |
| `PATCH /v1/settings/report` | Изменение личного состава отчёта |
| `GET /v1/users` | Реестр пользователей (админ) |
| `POST /v1/users` | Создание пользователя (админ) |
| `PATCH /v1/users/<id>` | Имя, логин, роль, включение (админ) |
| `DELETE /v1/users/<id>` | Удаление пользователя (админ) |
| `POST /v1/users/<id>/channels` | Привязка канала: `{"type": …, "ref": …}` |
| `DELETE /v1/users/<id>/channels` | Отвязка канала |

`POST /v1/control/actions` с `action=send_morning_report` собирает отчёт по
личному составу владельца токена.

Пользователь токена определяется по `device_id` (если устройство
привязано), затем по subject токена и логину веба. Привязка по `device_id`
позволяет развести пользователей мобильного клиента даже при общих
учётных данных веб-интерфейса:

```sh
curl -X POST https://<host>/v1/users/2/channels \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"type": "mobile", "ref": "<device_id>", "title": "Телефон Ивана"}'
```

## Как это работает при отправке

* **Отчёт** (`modules/morning_report.py`): данные мониторинга собираются
  один раз, затем для каждого получателя строится отчёт по его составу.
  Секции расширений кэшируются между получателями (`section_cache`) —
  тяжёлые live-секции (TLS, ресурсы, свободное место ZFS) опрашивают
  серверы один раз, а не на каждого пользователя.
* **Оповещения** (`lib/alerts.py`): `send_alert` получает адресатов из
  реестра, отфильтрованных по уровню, категории и личным тихим часам, и
  отправляет каждому в его чаты и комнаты.
